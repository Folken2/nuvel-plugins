# chief-of-staff 0.5 — task IDs

Date: 2026-11-17. Status: approved in chat ("let's do the task id").

## Why

Every radar rewrites its items as plain bullets. Nothing names "that item"
across runs, so:

- the user can't point at one ("that one is done", "snooze the Acme one")
  without describing it again, and the routines must guess which bullet they
  meant;
- no surface outside the chat (a board, a notification with buttons) can act on
  an item, because there is nothing stable to act on;
- we can't count how long a task lived, or whether it closed.

A stable task ID is the foundation for todos that people act on without
typing a paragraph into a chat: one-tap actions on a board, closing items from
evidence, and measuring time-to-done all need it.

## Goals

- Every actionable item in a radar has an ID that stays the same for as long
  as the task exists, in every section it moves through, and is never reused.
- The user, the main agent and any future surface can refer to a task by its
  ID alone, and handoffs can act on it.
- Works on the append-only registry, with storage connectors that can only
  create files, and needs no new folder or document kind.

## Non-goals

- The board / dashboard itself (next release; it will write handoffs that
  name task IDs).
- Closing items automatically from evidence (next release).
- Sending task IDs to nuvel. They are local counters; telemetry gets counts only.

## Design

### Format

`T-<n>`: the letter `T`, a hyphen and a positive integer with no padding
(`T-1`, `T-42`, `T-1307`). Short to say and type ("T-42 is done"), the same in
every language, and it can't be mistaken for a date, an amount or a `[project]`
tag.

In a radar, the ID is the first field of the bullet:

```
- T-42 — Send Acme the revised quote — Ana (Acme) — due 2026-11-20 — <link> — since 2026-11-17
```

A consumer finds tasks with `^- (T-\d+) — `.

### Which items get one

Items in *Needs you now*, *Decide*, *I owe*, *Waiting on*, *Watching* and
*Closed*. Not *Today* (meetings come from the calendar every run), not *Moving*
(a narrative), not *Journal* (it may mention IDs: "T-42 new", "T-17 closed").

### One task, one ID

- A task keeps its ID when it moves between sections (Waiting on → Needs you
  now when the reply arrives → Closed).
- *Needs you now* is a ranked view: a task there may also appear in its loop
  section (I owe, Waiting on) with the same ID. Two lines with the same ID are
  the same task; two different tasks never share an ID.
- **Matching before allocating:** a new finding belongs to a carried task when
  it is the same source thread (same thread / conversation ID or link) or the
  same commitment with the same person. Then update that task's line. Only a
  genuinely new task gets a new ID. When unsure, prefer the existing task and
  note the merge in the journal.
- **Never reused:** a closed task keeps its ID in *Closed* for 14 days, then
  drops off the snapshot; that number is never given out again.

### Allocation

The radar is the only skill that allocates IDs. The next free number is
carried in the radar's `## Cursors`:

```
- next_task: T-43
```

- New task → take `next_task`, then increase it by one.
- Each run computes `next_task` as the greater of the previous radar's
  `next_task` and (the highest ID in the previous radar + 1), so a damaged or
  hand-edited radar never makes an ID come back.
- **First run, or a radar from before 0.5** (no `next_task`, no IDs): number
  the carried items in section order (*Needs you now*, *Decide*, *I owe*,
  *Waiting on*, *Watching*, *Closed*), starting at `T-1`, and say so in the
  journal ("Task IDs assigned: T-1…T-12").
- Two radars started from the same previous radar could allocate the same
  number. The newest radar wins as always, so the other run's IDs were never
  current. Routines are scheduled hours apart, so this is accepted, not
  engineered away.

### Using IDs

- **Handoffs** get an optional `- task: T-42` line. A handoff with a task
  applies to that task only. A new instruction kind, `close`, lets the user
  mark a task done or not theirs (`- instruction: close — done` /
  `close — not mine`). It only changes the registry, so it stays inside the
  routines' read-only rule.
- **Radar** applies a `close` handoff by moving the task to *Closed* (with the
  reason), and applies a `remind` / `rank` / `ignore` handoff with a `task` to
  that task.
- **Recall** accepts IDs ("what's T-42?", "T-42 is done") and quotes them in
  answers. It writes a `close` handoff when the user says a task is done or
  not theirs.
- **Brief, prep, weekly review** keep the ID on every item they copy from the
  radar, so the user can reply with it.

### Telemetry

IDs are never sent. `radar.write` gets two counts: `tasks_new` (IDs
allocated this run) and `tasks_closed` (tasks moved to *Closed* this run).
`recall`'s routing gains `close`.

## Compatibility

- Readers of older radars (no IDs) keep working: an item without an ID is an
  item, and the next radar numbers it.
- Anything that parses radar bullets (e.g. a dashboard) must allow the leading
  `T-<n> — ` field.

## Test plan

- Structural tests: the registry contract defines the format, `next_task` and
  the migration rule; radar, recall and handoff docs mention them; trace
  catalogs list the new counts and routing.
- Manual: run a radar on a registry from 0.4.1 (IDs assigned, journal line),
  a second radar (same IDs carried, one new task gets `next_task`), and a
  "T-n is done" in recall followed by a radar (task in *Closed*).
